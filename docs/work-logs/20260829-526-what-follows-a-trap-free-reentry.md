`clean=0`이 그 문장입니다.

## 트랩은 어디에 떨어지는가

AOT 코드 캐시 안입니다. 로더가 캐시 베이스를 `0xF521B000`(그 실행에서)로 보고했고,
관측된 site가 전부 그 영역입니다.

```
[repiu-live-site] #4 F52A978E=1 F534A61B=1 F5356B76=1 F5350905=1
                     F52AB62D=1 F534A607=1 F5356C03=1 F5356BF9=1
```

**여덟 자리 모두 40만 건 동안 정확히 한 번씩만 나왔습니다.** 히스토그램은 8칸이 차면 그
여덟 개의 재등장만 세므로, 이 계측이 말할 수 있는 것은 **"처음 만난 여덟 자리는 다시
나타나지 않았다"**까지입니다. 모든 site가 서로 다르다는 주장은 이 데이터로 할 수 없습니다.

## 코드 읽기로 배제한 것

| 의심 | 결과 |
|---|---|
| 디스패치 썽크가 EFlags를 다르게 복원 | Linux `pushf/pusha … popa/popf/ret`, Windows `pushfd/pushad … popad/popfd/ret` — 동일 |
| Linux 폴트 핸들러가 EFlags 미반영 | 양방향 매핑 존재(`guest_cpu_context.cpp` 87·129행) |
| §8의 `requires Win32` 조기 반환 4곳 | `grep` 0건, 3d-20에서 제거됨 |

성공 경로는 TF를 지우고 캐시로 직행합니다. **코드상 트랩이 붙을 이유가 없는데 100% 붙습니다.**

## 아직 가설인 것 — 확인하지 않았습니다

`relinked=2,437,262`는 디스패치당 **6.09회**입니다. 같은 fixup을 계속 다시 박고 있다는
뜻일 수 있고, 그렇다면 캐시가 반복적으로 무효화·재구축되면서 **매번 새 INT3가 심어지는**
그림이 됩니다. 그것이 site가 재등장하지 않는 이유일 수도 있습니다.

**이것은 가설입니다.** 캐시 회수·격리 횟수를 재지 않았습니다. 다음 단계는 그 수치입니다.

## 정정

측정 도중 `elsewhere`가 breakpoint라고 단정해 보고했습니다. **그때 분류기는 단일 스텝만
제외하고 나머지를 한 통에 담고 있었으므로 근거가 없었습니다.** 종류를 가른 뒤에야
99.77% / 0.23%로 확인됐습니다. 결론은 같았지만 그때는 알 수 없었습니다.

## 고친 실수

* `snprintf` 인자만 늘리고 형식 문자열을 두어 형식/인자 불일치를 만들었습니다.
* C++ 리터럴의 `\n`을 Python heredoc으로 쓰다 실제 줄바꿈이 되어 리터럴이 갈라졌습니다.
  이 세션에서 네 번째입니다.
* 계측 블록을 `if (!g_started)` 조기 반환 블록 안에 삽입했습니다.
