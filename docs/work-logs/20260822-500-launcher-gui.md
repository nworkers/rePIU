## 2. 구현에서 갈린 판단들

### 2.1 왜 네이티브 GUI가 아닌가

**라이선스가 사실상 결정했습니다.** AGENTS는 GPL·LGPL·AGPL을 금지하는데, 리눅스에서 쓸
만한 크로스플랫폼 네이티브 툴킷은 Qt(LGPLv3/상용), GTK(LGPL), wxWidgets·FLTK(LGPL 파생)로
전부 그 계열입니다. 피하려면 Win32와 X11/Wayland를 각각 구현해야 하고, 같은 화면을 두세 번
만드는 일이 됩니다. Dear ImGui는 MIT라 정책에 걸리지 않고, 호스트가 이미 만드는 SDL3 창과
OpenGL 컨텍스트에 그대로 붙습니다.

여기에 두 가지가 더 붙습니다. **캐비닛에는 키보드와 마우스가 없으므로** 결국 게임 창 안에서
조작할 수 있어야 하고, **같은 레이어가 나중에 인게임 OSD**가 됩니다. 네이티브 런처 창은
둘 다 할 수 없습니다.

### 2.2 설정은 새 파라미터가 아니라 환경 변수로 게시합니다

vsync와 사운드 게인은 이미 `REPIU_GLIDE_SWAP_INTERVAL`과 `REPIU_YMZ_VOLUME`을 읽는
소비자가 있습니다. subsystem마다 새 파라미터를 통과시키는 대신, 런처가 저장값을 **그 환경
변수로 게시**합니다. 덕분에 변경 범위가 작고, 우선순위 규칙이 정확해집니다 — **호출자가
이미 설정한 변수는 절대 덮어쓰지 않으므로** 벤치마크 스크립트와 진단 절차가 계속 이깁니다.

게시 함수는 콜백을 받도록 만들어 probe가 프로세스 환경을 건드리지 않고 규칙을 검증합니다.

### 2.3 실행 불가 롬셋도 사유와 함께 보여줍니다

목록에서 감추면 "내가 가진 디스크가 왜 없지"가 되므로, 22개를 전부 보여주고 흐리게 처리한
뒤 사유를 그대로 씁니다(`ZIP 없음`/`필수 엔트리 없음`/`디렉터리 없음`/`CHD 없음`/`CHD 둘
이상`). 판정 규칙은 `PreparePiuChdMount`와 같은 것을 쓰되 **추출은 하지 않습니다** — 22개
디스크를 전부 무결성 검사하면 사람이 기다릴 수 없고, 진짜 판정은 실행 시점의 mount가 이미
합니다.

이를 위해 mount의 zip 검사를 `PiuRomZipHasRequiredEntries`로 노출했습니다. 규칙을 복제하지
않고 한 곳에 두기 위해서입니다.

### 2.4 진입 규칙은 기존 동작을 건드리지 않습니다

인자가 하나라도 있으면 런처는 아예 고려되지 않습니다. 인자가 없을 때만 열리고,
`REPIU_LAUNCHER=0`이 opt-out입니다(`ResolvePromotedToggle` 규약). 창이나 GL 컨텍스트를 만들
수 없는 환경에서는 런처를 포기하고 **기존 기본값으로 계속 진행**합니다 — 헤드리스에서
실행 자체가 실패하면 안 되기 때문입니다.

### 2.5 정정 — "같은 프로세스에서 계속 실행"은 틀린 결정이었습니다

설계는 자식 프로세스의 경로·환경 변수 문제를 피하려고 같은 프로세스에서 계속 실행하도록
정했고, 그대로 구현했습니다. **첫 실제 실행에서 게임이 시작되지 못했습니다.**

```
Win32 host first blocking block base: 0x00010000 size: 0x00003000 MEM_COMMIT
Win32 reservation error: 487 (VirtualAlloc MEM_RESERVE 실패)
Win32 relocated base candidate 0x01000000 ~ 0x09000000: 전부 occupied
Failed to reserve an available relocated image base
```

런처가 화면을 그리려고 GPU 드라이버를 로드하면서 게스트가 claim해야 할 저주소 공간을
선점했습니다. 고정 예약(0x10000~0x5E7000)이 막혔고 relocated image 후보가 전부 찼습니다.
인자를 주고 실행할 때는 런처가 뜨지 않으므로 멀쩡했고, 그래서 회귀 확인만으로는 잡히지
않았습니다.

**놓친 제약은 "게스트 주소 공간은 어떤 GPU 드라이버보다 먼저 확보되어야 한다"입니다.**
런처는 그리려면 드라이버를 로드할 수밖에 없으니 "먼저 그리고 나중에 실행"과 순서가 근본적으로
충돌합니다. 예약을 런처 앞으로 당기는 방법도 검토했지만, relocated image 후보 대역까지 미리
붙잡아야 하고 드라이버가 원하는 주소를 우리가 보장할 수 없어 취약합니다.

그래서 선택 결과를 새 프로세스로 넘깁니다. 자식은 롬셋 id를 인자로 받으므로 런처를 다시
열지 않고, 환경 변수를 상속하므로 방금 게시한 설정이 그대로 적용되며, 로거가 stderr에 쓰고
핸들이 상속되므로 리다이렉트한 로그에 부모와 자식 출력이 함께 남습니다.

명령줄 인용은 `BuildLauncherChildCommandLine`으로 분리해 probe가 검증합니다. 설치 경로에
공백이 있을 때만 깨지는 종류의 결함이라 개발 트리에서는 절대 드러나지 않기 때문입니다.

### 2.6 게임이 끝나면 런처로 돌아옵니다 (단독 실행에 한해)

첫 구현은 자식을 기다렸다가 그 종료 코드로 부모도 끝냈습니다. 그러면 게임을 한 번 하고
나면 rePIU를 다시 실행해야 합니다. 부모를 **세션의 프론트엔드**로 두고 런처 → 자식 실행 →
종료 대기 → 다시 런처를 반복하도록 바꿨습니다. 자식이 실패해도 종료 코드를 남기고 목록으로
돌아오므로, 프로세스가 조용히 사라지는 대신 이유를 보고 다시 고를 수 있습니다.

**복귀는 단독 실행에만 적용됩니다.** 커맨드라인으로 롬셋이나 실행 파일을 지정하면
`LauncherRequested()`가 인자 유무만 보고 즉시 false를 돌려주므로 런처 블록을 지나가지
않고, 게임이 끝나면 프로세스도 끝납니다. 런처가 띄우는 자식 역시 인자를 받으므로 같은
규칙으로 완전 종료합니다 — 루프는 그 종료를 관찰하는 부모에만 있습니다.

**루프로 바꾸며 생길 뻔한 버그.** 설정은 환경 변수로 게시하는데, 첫 실행 이후에는 우리가
게시한 변수가 "호출자가 설정한 변수"와 구분되지 않습니다. 그대로 두면 두 번째 실행부터
런처에서 바꾼 vsync·볼륨이 반영되지 않습니다. 호출자의 환경 상태를 루프 진입 전에 **한 번만
캡처**해 그 스냅샷으로 우선순위를 판단하도록 했습니다. 스크립트가 설정한 값은 여전히 이기고,
런처에서 바꾼 값은 매번 반영됩니다.

### 2.7 키보드로 롬셋을 고를 수 없었습니다

`ImGuiConfigFlags_NavEnableKeyboard`를 켠 것만으로는 부족했고, 사용자 확인에서 방향키가
아무 반응이 없었습니다. 원인이 둘 겹쳐 있었습니다.

* **focus가 움직여도 선택이 따라오지 않았습니다.** `Selectable`은 클릭이나 Enter처럼
  **활성화될 때만** true를 돌려줍니다. 방향키는 focus만 옮기므로 `selection`이 갱신되지
  않았고, 하이라이트는 제자리에 머물고 Start는 다른 롬셋을 실행했을 것입니다.
  `IsItemFocused()`로 focus를 따라 선택이 움직이게 했습니다.
* **첫 프레임에 focus 시작점이 없었습니다.** ImGui 내비게이션은 focus된 항목이 있어야
  방향키가 의미를 갖습니다. 창이 뜬 직후 현재 선택 행에 `SetKeyboardFocusHere()`로 focus를
  심었습니다. 마지막 실행 롬셋이 저장돼 있으면 그 행에서 시작합니다.

함께 두 가지를 정리했습니다. 실행 불가 롬셋에 `ImGuiSelectableFlags_Disabled`를 주어
**방향키가 건너뛰게** 했고(화면에는 사유와 함께 계속 보입니다), Enter는 실행·Space는 선택·
Esc는 종료로 나눠 목록에서 기대되는 관례에 맞췄습니다.

**교훈:** 키보드 조작은 "플래그를 켰다"로 끝나지 않습니다. 마우스로 확인한 화면은 키보드
경로가 비어 있어도 똑같이 동작하는 것처럼 보입니다.

## 3. 검증

* Win32 x86 **Debug/Release** `repiu`, `repiu_aot_probe` 빌드 성공. ImGui v1.92.1이
  FetchContent로 받아져 `repiu_imgui` 타깃으로 빌드됩니다.
* `repiu_aot_probe --launcher`: 5항목 전부 `true`.
  * `catalog_states` — 합성 디렉터리로 `ZIP 없음`·`필수 엔트리 없음`·`디렉터리 없음`·
    `CHD 없음`·`CHD 둘 이상`·`실행 가능` 여섯 상태를 만들고 각각 확인. 실행 가능일 때만
    CHD 경로가 채워지는 것까지 확인합니다.
  * `catalog_coverage` — 롬셋을 가진 내장 프로필 개수와 일치(22개 이상), 빈 `roms/`에서는
    전부 사유를 갖고 나타나며, 롬셋이 없는 `dos4gw_hello` 프로필은 제외됩니다.
  * `settings_round_trip` — 없는 파일, 왕복, 저장하지 않은 항목이 기본값으로 되살아나지
    않는 것, 잘못된 값이 경고만 남기고 나머지는 적용되는 것.
  * `environment_precedence` — 환경 변수가 없으면 게시, 있으면(빈 값이어도) 게시하지
    않음, 일부만 설정된 경우, 저장값이 없으면 아무것도 게시하지 않음.
  * `child_command_line` — 실행 파일 경로를 항상 인용해 `C:\Program Files\...`처럼 공백이
    있어도 인자 하나로 유지되는지, 롬셋이 비면 뒤에 구분자를 남기지 않는지(빈 인자를 주면
    자식이 다시 런처를 열게 됩니다).
* **완전 종료 확인.** 복귀 루프를 넣은 뒤 `repiu.exe pumpit8`을 다시 돌려 exit 0으로
  3.6초 만에 끝나고 런처 관련 줄이 0건임을 확인했습니다 — 인자를 준 실행은 루프에 들어가지
  않습니다.
* **회귀 확인.** `repiu.exe pumpit8`은 런처를 거치지 않고 그대로 pumpit8을 마운트했고,
  `REPIU_LAUNCHER=0`으로 인자 없이 실행하면 기존 기본값 `pumpit1`로 갔습니다. 두 로그 모두
  런처 관련 줄이 없습니다.
* **런처 창 확인.** 인자 없이 실행해 5초 뒤 프로세스가 살아 있고 창 제목이 `rePIU`임을
  확인한 뒤 종료했습니다.

## 4. 남은 것

* **화면 조작은 사용자 확인으로 끝냈습니다.** 목록 표시, 선택 실행, 게임 종료 후 런처
  복귀, 키보드 내비게이션을 사용자가 확인했습니다.
* 발판·캐비닛 버튼으로 런처를 조작하는 것은 범위 밖입니다. 지금은 키보드·마우스·게임패드로
  움직이며, ImGui 키보드/게임패드 내비게이션은 켜 두었습니다.
* 창 크기와 전체화면은 **넣지 않았습니다.** 현재 창 생성은 게스트가 요구하는 논리 해상도로
  결정되고 이를 바꿀 소비자가 없어서, Glide backend의 창 생성 경로를 함께 손대야 합니다.
  설계에는 후보로 적혀 있었으나 이번 범위에서 빼고 여기 남깁니다.
* 인게임 OSD는 다음 작업입니다. `launcher_ui`가 SDL3와 ImGui만 쓰므로 같은 레이어를 게임
  창에 얹는 형태가 됩니다.

# Launcher GUI Work Log

Design: [20260822-500-launcher-gui.md](../design/20260822-500-launcher-gui.md)

Work order: [20260822-500-launcher-gui.md](../work-orders/20260822-500-launcher-gui.md)

## Result

Running with no arguments opens a launcher listing every ROM set and starts the selected one in a
fresh process, a correction to the design explained below; an argument-bearing invocation is
untouched. New platform-neutral
`launcher::RomSetCatalog` and `launcher::LauncherSettings` carry the availability rules and the
`cfg/repiu.ini` storage, `launcher::RunLauncherUi` draws the screen with SDL3, OpenGL, and Dear
ImGui, the mount's ROM-zip precondition is exposed as `PiuRomZipHasRequiredEntries` so the rule
lives in one place, and `main.cpp` keeps only the wiring.

## Judgement calls

**Why not a native GUI.** Licensing effectively decided it: every cross-platform native toolkit
that would serve Linux is LGPL-family and the project forbids copyleft, so avoiding them would mean
implementing the same screen separately for Win32 and X11/Wayland. Dear ImGui is MIT and attaches
to the SDL3 window and OpenGL context the host already creates. Two further reasons point the same
way — cabinets have no keyboard or mouse, so the UI must eventually be operable inside the game
window, and the same layer becomes the in-game OSD later. A separate native window can do neither.

**Settings are published as environment variables rather than threaded as parameters.** Vertical
sync and sound gain already have consumers reading `REPIU_GLIDE_SWAP_INTERVAL` and
`REPIU_YMZ_VOLUME`, so the launcher publishes its stored values into those names instead of adding
a parameter to every subsystem. That keeps the change small and makes the precedence rule exact: a
variable the caller already set is never overwritten, so benchmark scripts and diagnostic
procedures keep winning. The publishing function takes a callback so the probe verifies the rule
without touching the process environment.

**Unavailable ROM sets stay visible with their reason.** Hiding them would leave an operator asking
why a disc they own is missing, so all twenty-two are listed and dimmed with the specific cause.
The rules match `PreparePiuChdMount` but extract nothing, because verifying twenty-two discs would
outlast anyone's patience and the real judgement already happens at launch.

**Correction: continuing in the same process was the wrong decision.** The design chose it to avoid
child-process path and environment plumbing, and it was implemented that way. The first real run
never reached the game: the launcher had to load a GPU driver to draw, and that driver claimed the
low address space the guest must reserve, leaving the fixed reservation at `0x00010000` blocked by
a committed 12 KiB block and every relocated-image candidate from `0x01000000` through `0x09000000`
occupied. An argument-bearing run never opens the launcher, which is why the regression checks
stayed green through it. The constraint that was missed is that the guest address space has to be
claimed before any GPU driver loads, and a launcher cannot draw without loading one; reserving ahead
of the launcher was considered but would have to hold the relocated-image candidates too and cannot
guarantee the addresses a driver wants. The selection is therefore carried into a fresh process,
which inherits the published environment and stderr, and command-line quoting is factored into
`BuildLauncherChildCommandLine` and probed, because a path with a space is the failure that only
appears outside a developer's tree.

**A finished game returns to the launcher, but only when rePIU was started standalone.** The first
implementation waited for the child and exited with its code, which meant playing one game and then
starting rePIU again. The parent is now the session's front end: launcher, child, wait, launcher.
A failed child returns to the list with its exit code logged rather than vanishing. Passing a ROM
set or an executable path on the command line bypasses the launcher entirely and ends the process
when the game ends, and the child the launcher spawns takes an argument, so it follows that same
rule -- the loop exists only in the parent that watches it. One bug this nearly introduced: after
the first launch, the variables the launcher published are indistinguishable from ones the caller
set, so a second change to vertical sync or volume would have been ignored. The caller's
environment is therefore captured once, before the loop, and that snapshot decides precedence.

**Keyboard selection needed more than the navigation flag.** A user check found the arrow keys
dead. `Selectable` returns true only on activation, so moving focus never updated the selection and
Start would have run whatever the mouse last chose; the selection now follows `IsItemFocused()`. And
navigation had no starting point on the first frame, so focus is planted on the current selection
when the window appears. Unavailable rows became `ImGuiSelectableFlags_Disabled` so the arrows skip
them while their reasons stay visible, and Enter starts, space selects, Escape quits. The lesson is
that enabling the flag is not the same as having a keyboard path: a screen verified with a mouse
looks identical when that path is missing.

**Existing invocations are untouched.** Any argument bypasses the launcher entirely; it opens only
with none, and `REPIU_LAUNCHER=0` opts out. When a window or GL context cannot be created the
launcher steps aside and the previous default target runs, so a headless host still starts.

## Verification

Debug and Release builds of `repiu` and `repiu_aot_probe` succeeded with ImGui v1.92.1 fetched and
built as `repiu_imgui`. `repiu_aot_probe --launcher` passed all five checks: the six availability
states over synthetic directories, catalog coverage against the built-in profiles including the
skipped non-ROM-set profile, settings round trip with a missing file and malformed values,
environment precedence in every combination, and child command-line quoting including a path
containing spaces. For regression, `repiu.exe pumpit8` mounted pumpit8
with no launcher involvement and `REPIU_LAUNCHER=0` with no arguments went to the old `pumpit1`
default. The launcher itself was confirmed to open: the process was alive after five seconds with
window title `rePIU`.

## Remaining

The screen's behavior needs a user's eyes — listing, launching, and saving options. Panel-driven
navigation is out of scope; keyboard, mouse, and gamepad navigation are enabled. Window size and
fullscreen were **not** implemented: window creation currently follows the guest's logical
resolution and no consumer exists for an override, so it would mean touching the Glide backend's
window path. The in-game OSD is the natural next task, reusing this same layer.
