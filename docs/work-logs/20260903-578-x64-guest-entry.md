# 작업 기록 20260903-578 — x64 guest entry: code cache로 들어가기

설계: [20260903-578](../design/20260903-578-x64-guest-entry.md) ·
작업 지시: [20260903-578](../work-orders/20260903-578-x64-guest-entry.md)

## 결과 — x64에서 게스트가 실행됐고, 게스트 fault로 멈췄습니다

```text
[repiu-fault] unhandled signal=0xb eip=0x20000005 access=0x0
```

**이 프로젝트에서 x64가 게스트 명령을 실행한 첫 기록입니다.** 정지 지점이
`minimal original entry execution requires a 32-bit host`에서 **code cache 안의
주소**로 옮겨갔습니다.

## 구현

설계 결정대로 세 조각을 넣었습니다.

- `IsCodeCacheEntrySupported()` — `IsDirectX86ExecutionSupported`를 **거짓말시키지
  않았습니다.** 그 함수는 "게스트 자신의 바이트로 뛰어들 수 있는가"를 묻고 x64에서
  답은 진짜로 아니오입니다. 새 술어는 다른 질문입니다.
- `guest_entry_x64.S` — probe 브리지와 같은 모양. guest GPR을 host 동번호
  레지스터에, guest ESP를 `R15D`에 32비트 이동으로(상위 절반은 하드웨어가 0으로).
- `LinuxX64EngineResolver` — `FindAotCacheAddress` 위의 어댑터. 0을 답하면 Task
  562의 thunk가 `INT3`을 놓습니다.

## 설계가 놓친 것 — 울타리는 둘이 아니라 셋이었습니다

설계는 `IsDirectX86ExecutionSupported` 하나를 라우팅 대상으로 적었습니다. 그것을
열자 실행이 **두 번째 울타리**에서 멈췄습니다.

```text
[loader] Win32 minimal execution message:
         guest stack execution requires a 32-bit x86 host
```

`use_guest_stack`이 참인데 `IsGuestStackSwitchSupported()`가 거짓이었습니다.
설계는 그 술어를 x64에서 false로 **유지한다**고 적었고 그 판단 자체는 옳았습니다 —
x64에는 되돌릴 전환이 없습니다. 놓친 것은 **호출자가 요구하는 것이 "전환"이 아니라
"게스트가 자기 스택 위에서 돈다"**는 것이고, x64는 그것을 전환 없이 이미
만족시킵니다(진입이 `R15D`에 guest ESP를 심으므로).

그래서 술어는 그대로 두고 **거절 조건**을 두 메커니즘을 아는 형태로 고쳤습니다.
`IsDirectX86ExecutionSupported`에 적용한 것과 같은 논리를 한 번 더 적용한
것입니다. 설계가 그 자리를 미리 보지 못한 것이 이번 단위의 예측 실패입니다.

## 측정을 위해 계측 하나를 추가했습니다

첫 실행이 `exit=139`로 끝났고, **어디서인지 알 방법이 없었습니다.** Windows에는
`InstallHostCrashReporter`가 있지만 그 함수의 본문은 `#if defined(_WIN32)`
전체이고, Linux에는 아무것도 없습니다. WSL에 gdb도 없습니다.

그래서 fault handler의 미처리 경로에 한 줄을 추가했습니다 — signal, `Eip`,
접근 주소를 `write(2, ...)` 하나로 씁니다. 서식 라이브러리도 할당도 잠금도 없이
async-signal-safe하게, 프로세스가 죽기 직전에 실행되는 handler이므로.

이것은 범위 확대가 아니라 **이 단위가 산출해야 할 관측 그 자체**입니다. 그것
없이는 "정지 지점을 기록한다"는 완료 조건을 만족할 수 없었습니다.

## 관측

| | Task 577 | Task 578 |
|---|---|---|
| `minimal execution supported` | false | **true** |
| 정지 메시지 | `requires a 32-bit host` | (없음 — 게스트가 실행됨) |
| 종료 | exit 0, 게스트 미실행 | **exit 139 (SIGSEGV), 게스트 실행 중** |
| 정지 주소 | — | **`eip=0x20000005 access=0x0`** |

cache base는 `0x20000000`이고 entry도 같으므로, fault는 **cache 진입 5바이트
지점**입니다.

### 그 지점이 무엇인지

게스트 entry는 `0x010F16B0`이고 바이트는 `eb 76` — Watcom 배너 문자열을 건너뛰는
short jump 하나뿐인 block입니다. long mode에서 `E9 rel32` 5바이트로 방출되므로
`0x20000005`는 **두 번째로 방출된 block의 시작**입니다.

점프 대상 `0x010F1728`의 바이트:

```text
fb              sti
83 e4 fc        and esp, -4
89 e3           mov ebx, esp
89 1d 40661a01  mov [0x011A6640], ebx
...
```

**여기서 관측과 예상이 어긋납니다.** `sti`는 privileged이므로 분류기가 거절하고
long mode는 `INT3`을 놓아야 하며, 그렇다면 `SIGTRAP`(0x5)이 나와야 합니다.
관측된 것은 `SIGSEGV`(0xb)이고 접근 주소는 0입니다.

**이 불일치는 이 단위에서 해결하지 않습니다.** 확정하려면 방출된 캐시 바이트를
실제로 덤프해야 하고, 그 도구는 지금 없습니다. 추측으로 결론을 적는 것이 이
세션에서 세 번 반증된 방식이므로(574·575·577), 관측만 기록하고 다음 단위에
넘깁니다.

## 검증

|---|---|
| x64 `repiu` 실행 | **정지 지점 이동** — 게스트 실행, cache+5에서 SIGSEGV |
| 예산 안 종료 | 크래시로 즉시 종료(무한 대기 아님) |
| Linux x64 `repiu_core_probe` | 20/20, failures 0 |

작업 지시의 완료 조건 "정지 지점이 이동하고 새 지점이 관측으로 기록될 것"을
만족합니다.

## 남은 것

| # | 항목 | 상태 |
|---|---|---|
| 0~2 | long-mode 방출 / 심볼 / `Esp` | 해결 |

항목 6이 다음입니다. 첫 필요한 것은 **방출된 캐시 바이트를 덤프하는 수단**입니다 —
`sti`가 무엇으로 방출됐는지 보면 `SIGTRAP`이어야 할 자리에서 `SIGSEGV`가 난 이유가
결정됩니다.

## 아직 확인하지 않음

- **다른 ROM 세트**로 돌려 보지 않았습니다. 관측은 `pumpit2a` 한 번입니다.
- 항목 5(dynamic append의 validator)는 여전히 도달되지 않았습니다. 게스트가 첫
  block도 넘기지 못했으므로 append까지 가지 못합니다.
- 새 fault 보고는 x64에서만 관측됐습니다. i386 경로에서 그것이 찍히는 상황은
  만들어 보지 않았습니다.

# Work log 20260903-578 — The x64 guest entry: into the code cache

Design: [20260903-578](../design/20260903-578-x64-guest-entry.md) ·
work order: [20260903-578](../work-orders/20260903-578-x64-guest-entry.md)

## Result — a guest executed on x64, and stopped at a guest fault

```text
[repiu-fault] unhandled signal=0xb eip=0x20000005 access=0x0
```

**This is the first record of x64 executing a guest instruction in this
project.** The stopping point moved from `minimal original entry execution
requires a 32-bit host` to **an address inside the code cache**.

## Implementation

The three pieces the design named:

- `IsCodeCacheEntrySupported()` — `IsDirectX86ExecutionSupported` was **not made
  to lie.** It asks whether the guest's own bytes may be jumped at, and on x64
  the answer is genuinely no. The new predicate is a different question.
- `guest_entry_x64.S` — the probe bridge's shape: guest GPRs into the host
  registers of the same number, guest ESP into `R15D` with a 32-bit move so the
  hardware zeroes the upper half.
- `LinuxX64EngineResolver` — an adapter over `FindAotCacheAddress`. Answering
  zero makes Task 562's thunk plant an `INT3`.

## What the design missed — there were three fences, not two

The design named `IsDirectX86ExecutionSupported` as the fence to route. Opening
it moved execution to a **second** one:

```text
[loader] Win32 minimal execution message:
         guest stack execution requires a 32-bit x86 host
```

`use_guest_stack` was true and `IsGuestStackSwitchSupported()` was false. The
design said to **keep** that predicate false on x64 and that judgement was right
— there is no switch to undo. What it missed is that **what the caller asks for
is not "a switch" but "the guest runs on its own stack"**, and x64 already
satisfies that without one, because the entry seeds guest ESP into `R15D`.

So the predicate stayed and the **refusal** was taught about both mechanisms —
the same logic already applied to `IsDirectX86ExecutionSupported`, applied once
more. Not seeing that site in advance is this unit's failed prediction.

## One instrument was added, because the measurement needed it

The first run ended in `exit=139` with **no way to know where.** Windows has
`InstallHostCrashReporter`, but that function's whole body is inside
`#if defined(_WIN32)` and Linux has nothing. There is no gdb in this WSL either.

So the fault handler's unhandled path gained one line: the signal, `Eip`, and
the access address, written with a single `write(2, ...)`. No formatting
library, no allocation, no locking — async-signal-safe, because it runs on a
handler that is about to let the process die.

This is not scope creep but **the observation this unit exists to produce**.
Without it the completion criterion "record where it stops" could not be met.

## The observation

| | Task 577 | Task 578 |
|---|---|---|
| `minimal execution supported` | false | **true** |
| Stopping message | `requires a 32-bit host` | (none — the guest ran) |
| Exit | 0, no guest | **139 (SIGSEGV), guest running** |
| Stopping address | — | **`eip=0x20000005 access=0x0`** |

The cache base is `0x20000000` and so is the entry, so the fault is **five bytes
into the cache**.

### What sits there

The guest entry is `0x010F16B0`, bytes `eb 76` — a block of one short jump over
the Watcom banner string. Long mode emits that as a 5-byte `E9 rel32`, so
`0x20000005` is **the start of the second emitted block**.

The jump target `0x010F1728` reads:

```text
fb              sti
83 e4 fc        and esp, -4
89 e3           mov ebx, esp
89 1d 40661a01  mov [0x011A6640], ebx
...
```

**Here the observation and the expectation disagree.** `sti` is privileged, so
the classifier refuses it and long mode should plant an `INT3` — which would
raise `SIGTRAP` (0x5). What was observed is `SIGSEGV` (0xb) with an access
address of zero.

**This discrepancy is not resolved here.** Settling it means dumping the emitted
cache bytes, and no tool does that today. Writing down a guess as a conclusion is
the method this session has had refuted three times (574, 575, 577), so only the
observation is recorded and the diagnosis goes to the next unit.

## Verification

|---|---|
| x64 `repiu` run | **stopping point moved** — guest runs, SIGSEGV at cache+5 |
| Finishes within budget | ends immediately on the crash, not a hang |
| Linux x64 `repiu_core_probe` | 20/20, 0 failures |
| Linux i386 `repiu` link | succeeds |
| Linux i386 `repiu_core_probe` | 19/19, 0 failures |
| Win32 `repiu_aot_probe` | 41 `_all=true`, 0 `_all=false` |

The work order's completion criterion — the stopping point moves and the new
point is recorded as an observation — is met.

## Not yet verified

- No **other ROM set** was tried; the observation is one run of `pumpit2a`.
- Item 5 (the validator on dynamic append) is still unreached — the guest does
  not get past its second block, so append never runs.
- The new fault report has only been seen on x64. No situation was constructed
  to make it print on the i386 path.
